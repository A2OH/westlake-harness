# audio-tone probe

A pure-Java app that plays a steady tone through each Android audio path in turn, looping, so one
recording of the board's output covers them all. Each path has its own frequency:

| letter | tone | path |
|---|---|---|
| A | 1000 Hz | AudioTrack, 48 kHz stereo 16-bit, blocking short[] writes |
| B | 1500 Hz | AudioTrack, 44.1 kHz stereo 16-bit, blocking short[] writes |
| C | 2500 Hz | AudioTrack, 48 kHz stereo float, non-blocking ByteBuffer writes (ExoPlayer's pattern) |
| M | 2000 Hz | MediaPlayer on a 44.1 kHz stereo WAV asset (generated by build.sh) |

    ./build.sh                          # out/audio-tone-probe.apk
    # launch it, then record with probes/audio-capture/oh_record (source 2)
    python3 tone_timeline.py recording.wav

A correct path shows solid runs of its letter at its exact frequency, about 4 s per round. A path
at the wrong rate shifts its tone; one that drops data leaves '.'; one that corrupts samples shows
'?'.

## Found with it (2026-09-28)

AudioTrack float through a ByteBuffer played as loud broadband noise for 7 s instead of 4: the
bridge's AudioTrack shim passed the float bytes to a 16-bit renderer. Fixed in westlake by
rebinding native_write_native_bytes (conversion to 16-bit, then the bridge's 16-bit write). After
the fix all four paths play their exact tone with no gaps, and sound clean by ear.

Measuring noise from the capture needs care: a playback-capture block has a seam at sample
718-719 (present for OHAudio's own renderer too), so sine-fit residuals and "clicks" there are the
capture's, not the audio's. The tone samples between seams are bit-exact.
